# copilot.md

## Purpose

Implement a lightweight anatomic pathology LIS as a **monorepo** with:

- **Backend:** Node.js + Express
- **Database:** PostgreSQL
- **ORM / migrations / seed:** Prisma
- **Frontend:** React + Vite + MUI
- **Testing:** lint + backend tests + frontend component tests + Playwright E2E
- **Local orchestration:** Docker Compose
- **Developer tooling available in repo/environment:** Prisma, Vite, PostgreSQL MCP, Playwright MCP, GitHub MCP, CI/CD, Docker Compose

Copilot should generate code and structure that is **production-leaning, modular, and maintainable**, while keeping scope aligned to a lightweight LIS rather than a full enterprise system.

## Authentication / login requirements

Implement a **simple passwordless login flow**.

Behavior:
- User is presented a login page.
- They can:
  - search existing employees by name or username and choose one, or
  - enter a new employee
- If entering a new employee:
  - create an `employee` record in the database
  - require at minimum:
    - first name
    - last name
    - username
    - employee role
- Roles supported:
  - `Pathologist`
  - `Technologist`

This is **not secure enterprise authentication**. It is a lightweight session identity mechanism for demo/prototype use.

Implementation guidance:
- Use an Express session or signed cookie with minimal session state.
- Store current logged-in employee identity in session.
- Protect app routes after login.
- Add a backend middleware that injects current employee context.
- Do not implement passwords, OAuth, LDAP, or SSO in this phase.
- Structure auth code so a real auth provider can replace it later.

## Important schema behaviors

### Order IDs

`order_id` is the case ID and must be generated by the backend as:

```text
SU + 2-digit current year + 7-digit sequence restarting each year
```

Example:
- `SU250000001`
- `SU250000002`

Rules:
- The sequence resets each year.
- ID generation must happen on the backend only.
- It must be concurrency-safe.

Implementation guidance:
- Do **not** generate IDs in frontend.
- Use a transaction-safe sequence strategy.
- Recommended approach:
  - create a dedicated table like `order_sequence_year`
  - fields:
    - `year_two_digit`
    - `last_value`
  - update inside a database transaction
- Avoid race-prone “max + 1” logic without locking.

### Specimen IDs

Generate automatically on backend:

```text
{order_id}-A
{order_id}-B
...
{order_id}-Z
{order_id}-AA
{order_id}-AB
...
```

Rules:
- Increment within each order.
- Need a deterministic suffix generator supporting Excel-like alphabetic progression.

### Block IDs

Generate automatically on backend:

```text
{order_id}-{specimen_code}{block_number}
```

Examples:
- `SU250000001-A1`
- `SU250000001-A2`

### Slide IDs

Generate automatically on backend:

```text
{order_id}-{specimen_code}{block_number}-S{slide_number}
```

Examples:
- `SU250000001-A1-S1`
- `SU250000001-A1-S2`

Rules:
- `slide_number` is the only “level” indicator needed.
- Do not add a separate slide-level field.

## Report versioning requirements

Reports are versioned and prior versions must remain immutable.

Behavior:
- An order can have multiple reports.
- Each report has `version_number`.
- `pathologist_employee_id` is the sign-out user identity.
- `signed_out_datetime` records sign-out time.
- `is_amendment` marks amendment/addendum style revisions.
- `supersedes_report_id` links report-to-report lineage.
- `orders.is_reactivated` indicates case was reopened.
- `orders.reactivated_from_report_id` points to the report that triggered reactivation.

Required workflow:
1. User enters or edits a draft result.
2. On sign-out:
   - persist report as signed-out
   - set `signed_out_datetime`
   - mark as final where appropriate
3. On reactivation:
   - the existing signed-out report remains unchanged
   - the order is marked reactivated
   - create a new draft version linked via `supersedes_report_id`
4. Revised/addended sign-out creates a new report version

Do not mutate prior final report content in place.

## Report files / PDF storage requirements

The schema includes `report_file`, but **do not use DB blob storage in runtime practice** for primary file persistence.

Implementation expectation:
- Store generated PDFs in the filesystem for local/dev use.
- Keep DB schema compatible with future object storage.
- `report_file` should store metadata and file reference, not large binary payloads in active implementation.

Add practical fields in application/Prisma if needed, such as:
- `storage_path`
- `original_file_name`
- `mime_type`
- `file_type`
- `created_at`

If the database schema still conceptually includes blob storage, treat that as future-facing and do not build the app around DB binary storage.

Preferred dev storage path:
```text
/apps/backend/storage/report-files/
/apps/backend/storage/generated-pdfs/
```

Ensure:
- directories are created automatically on startup or on first use
- files are gitignored
- Docker volume mounts preserve generated files in local dev

## Domain assumptions to implement

Use the following assumptions unless code context strongly requires a small adjustment:

- `order_id` is the accession/case identifier.
- `registered_date` is the accessioned timestamp.
- `completed_date` can reflect final completion.
- processing queue default means no existing blocks or slides.
- result queue requires at least one block or slide and no signed-out final latest report.
- report versions are immutable once signed out.
- latest report version is the one with highest `version_number`.
- reactivation creates a new report draft rather than editing an old report.
- printable outputs are PDFs downloaded from backend endpoints.
- runtime file storage is filesystem-based for now.
