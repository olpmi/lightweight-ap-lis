# Verification evidence behind the manuscript

Every quantitative claim the manuscript makes about this system is produced by a
committed script and can be regenerated by a reviewer. Nothing below is hand-typed —
that is how "250 synthetic cases" and "147 tests" reached earlier drafts when the
seed had always created 300 and the suite had grown past 300 cases.

**Status.** This file was originally a set of proposed corrections and drop-in
paragraphs. Those were applied to the manuscript on 2026-08-13, so it is now a
record of what the paper reports and how to reproduce it, not a proposal. Where the
paper and this file ever disagree, regenerate and trust the artifact.

The first four are produced by the manual **Verification Report** workflow
(`.github/workflows/verification.yml`), so the numbers name the CI run that produced
them. The last two cannot be: they characterise a host, and a shared runner would
yield figures with no deployment meaning. Those are run by a person on a named
machine.

## What the manuscript reports

**Automated tests** — 329 cases across 39 files: 323 passed, none failed, six
skipped. The six are opt-in Playwright specs that record demonstration videos and
audit translation coverage rather than verify behaviour. Statement coverage was
72.4% backend and 44.5% frontend. Backend integration suites require `DATABASE_URL`
and `SESSION_SECRET`; without them the database-backed cases do not execute, which
the generated report records explicitly rather than counting as passes.

**Synthetic corpus** — 300 cases, 190 surgical pathology and 110 cytology, stratified
across the workflow (20 accessioned only, 60 with blocks, 60 awaiting sign-out, 150
signed out, 10 amended) then deterministically shuffled so accession order does not
encode workflow stage. 50 patients, 595 specimens, 1078 blocks, 1809 slides, 260
reports. Generated by a fixed-seed linear congruential generator rather than
`Math.random`, so regeneration on a different host and Node version reproduces the
characterisation byte-for-byte apart from its commit and timestamp stamps.

**Data model** — 18 relational entities, from 22 `model` blocks excluding four
structural tables: `AncillaryPanelItem` (join), `OrderSequenceYear` and
`PatientSequence` (identifier-sequence counters), and `CustomTemplateTranslation`
(translation side-table). The rule is printed beside the number so a reviewer can
recompute it.

**Resource footprint and latency** — measured on a Dell Latitude 5520 (Intel Core
i5-1135G7, four cores, 2.40 GHz; 16 GB RAM) under Docker Desktop with the WSL2
backend, chosen as representative of hardware a resource-constrained laboratory
would plausibly own rather than of server-class provisioning. Idle single-node
footprint 160.09 MB; replicated primary and hot standby 199.28 MB; storage 5.9 KB
per case. Full accessioning-to-sign-out 1107.3 ms at the median, sign-out 970.6 ms,
with no errors in any scenario including 25 simultaneous authenticated sessions.

A Dell Precision 5860 (Xeon w5-2555X, 14 cores, 63.25 GB) was profiled as an upper
bound: idle 130.4 MB single-node, 187.6 MB replicated. Storage per case was
identical on both hosts.

## Disclosures the manuscript carries

The corpus is stratified to populate every workflow stage but is not clinically
representative. Body sites are drawn from the full anatomic lookup independently of
case type, so some cytology cases carry anatomically implausible sites. Every
ancillary order in the corpus is a routine haematoxylin and eosin order, so
immunohistochemistry, special-stain, molecular and send-out ordering are exercised
by automated tests rather than by seeded data. The corpus contains no preliminary
reports and no addenda, and it reuses 50 patients across 300 cases, so the
per-patient storage contribution is lower than a deployment where every case is a
distinct patient.

Several implemented behaviours remain outside automated coverage: manual case-status
transitions, block-level haematoxylin and eosin status transitions, and the workflow
guards that reject premature sign-out.

The test suite and the corpus were both written by the authors. Verification here
means the implementation behaves as specified; it establishes nothing about clinical
safety, usability, workflow suitability or operational effectiveness, and no
independent or third-party verification has been undertaken.

## Deliberately not published

**Peak memory under load.** Two runs on one machine gave 640.9 MB and 430.9 MB for
identical work. Headless Chromium retains memory across the benchmark's render
iterations, so the peak is a property of the workload at its configured iteration
count rather than of the system. Reported qualitatively — rendering dominates the
memory profile as well as the latency profile — and not as a figure.

**Idle CPU as a point value.** Measured p50 0.03% with transients to 18%. A single
sample landing anywhere in that range is how the indefensible "CPU utilization
< 0.5%" row entered an earlier draft. The row was deleted; the profiler now reports
min/p50/max rather than a point estimate.

**Storage growth as a before/after delta.** Only 1.73 MB of the 10.8 MB corpus
database is case data, the rest being PostgreSQL's own catalogues and write-ahead
log, so 91 inserted cases sat inside the noise floor of catalogue churn and vacuum
reclamation. One run reported growth of −56.0 KB — the database shrank while cases
were added — and another +2 KB per case. Replaced by an absolute quiesced
measurement of the case-scaling tables, which returned 5.9 KB per case identically
across six runs on two machines.

## Defects found during verification, since fixed

These are the substantive result of the verification exercise. Each was invisible to
the test suite as it stood, and two would have made published claims untrue.

**Report PDFs were never generated.** The production renderer launched headless
Chromium with `--single-process` and `--no-zygote`; modern Chromium exits immediately
under that combination. Because sign-out deliberately catches PDF errors so they
cannot block a clinical action, the failure was silent — cases signed out, reported
success, and produced no PDF and no stored file record. In the deployment container
image, zero report PDFs had ever been produced.

**Patient identifiers repeated every 2.8 hours.** Identifiers were derived from
`Date.now()` truncated to seven digits, which wraps every 10,000,000 ms, and patient
lookup returned any record matching a supplied identifier without comparing name,
date of birth, or sex. A newly registered patient could therefore be silently merged
into an unrelated earlier record and their case filed under the wrong person.
Allocation now comes from a database sequence via a single atomic increment.

**Amended cases never returned to the work queue.** The result-queue predicate
excluded any case with a signed-out report; after an amendment the superseded version
still satisfied it, so a case awaiting a revised sign-out disappeared from the
pathologist's worklist and was reachable only by search. Ten of the 300 corpus cases
are affected, which is why the result queue holds 70 rather than 60.

**The pessimistic edit-lock was advisory.** `assertHolder()` was implemented but had
no call sites, so a client bypassing the UI lock could write to a case another user
was editing. It is now called inside the transactions that create drafts, sign out,
sign preliminary reports, and reactivate.

**The benchmark stopped measuring the production renderer.** Enforcing
Administrator-only access on the report-layout preview route left the benchmark
driving it with a pathologist session, so all 30 calls returned 403 and the renderer
— the dominant cost of sign-out — silently vanished from the results table rather
than failing loudly. The benchmark now opens a second session as the seeded
Administrator and reports the absence of one against that scenario.

## Maintaining Supplementary Table S2

The workflow-to-test-layer mapping is the one table here without a generating
script, because "which layer exercises this workflow" is a judgement rather than a
count. When a workflow gains or loses coverage, update it by hand and say so in the
commit. Candidates currently unlisted: patient identification, and the three-role
authorization model.
